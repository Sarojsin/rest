# Database Schema Specification

**Database recommendation:** PostgreSQL  
**Status:** Logical schema contract; not executable DDL and not a substitute for reviewed Alembic migrations.

This document defines the minimum domain model and integrity rules. It deliberately separates order workflow, kitchen progress, billing, and payment state. Implementations may split or combine physical tables only if they preserve these invariants and document the reason.

## 1. Global conventions

- Use `UUID` primary keys, generated by the application or PostgreSQL. UUIDs are identifiers, not access credentials.
- Use `TIMESTAMPTZ` and store timestamps in UTC. Display/report using the restaurant's configured IANA timezone.
- Use `BIGINT` integer minor units for money (for example, `amount_minor`) plus an ISO 4217 currency code. Do not use `FLOAT`/`DOUBLE PRECISION` for money. Tax and rounding rules must be explicit and validated for the pilot jurisdiction.
- Use `NUMERIC(12,3)` for measured inventory quantities; define the unit and conversion rules. Do not use binary floating point for stock quantities.
- Store foreign keys, unique constraints, and check constraints in the database, not only in Pydantic models.
- Add `created_at` and `updated_at` to mutable entities. Use `created_at` plus actor information for append-only ledger/audit tables. Do not update `created_at`.
- Use soft-disable/archive flags for catalog entities that may be referenced by historical records. Do not hard-delete historical orders, bill lines, payments, refunds, stock movements, or audit events.
- `restaurant_id` is required on tenant-owned tables unless a table is strictly global (e.g. a code-defined permission catalog). Add a tenant-aware index to each common tenant query.
- Prefer explicit columns over unvalidated JSON blobs for fields used in authorization, financial calculations, filtering, or reporting. JSONB is appropriate for immutable snapshots and provider metadata after sensitive fields are redacted.
- Every write that changes a business status must record actor/time and follow an allowed transition.

## 2. Tenant and identity model

### 2.1 `restaurants`

Represents one customer organization/restaurant tenant.

| Column | Type | Rules |
|---|---|---|
| `id` | UUID PK | Stable tenant identifier |
| `name` | VARCHAR(160) | Required |
| `slug` | VARCHAR(80) | Unique, normalized; not an authorization secret |
| `status` | ENUM/text | `ACTIVE`, `SUSPENDED`, `CLOSED` |
| `timezone` | VARCHAR(64) | Valid IANA timezone |
| `currency_code` | CHAR(3) | ISO 4217 code; validate supported currencies |
| `created_at`, `updated_at` | TIMESTAMPTZ | UTC |

### 2.2 `restaurant_settings`

One settings row per restaurant (`restaurant_id` PK/FK).

Recommended fields include `locale`, `business_day_start_local`, `tax_configuration_ref` or explicit tax rules, `receipt_header`, `receipt_footer`, `qr_ordering_enabled`, `online_payments_enabled`, `menu_published_at`, `settings_version`, `created_at`, and `updated_at`.

Do not put gateway secrets or passwords in this table. Store a secret-manager reference or retrieve credentials through deployment secret configuration. Tax settings should be versioned so the applicable configuration can be identified for historical documents.

### 2.3 `users`

Represents a person/login identity, not their access to a specific restaurant.

Recommended fields: `id UUID PK`, normalized unique `email` or `phone_e164` (depending on the approved login design), `password_hash` when password authentication is used, `display_name`, `status` (`ACTIVE`, `LOCKED`, `DISABLED`), `email_verified_at`, `phone_verified_at`, `last_login_at`, `created_at`, `updated_at`.

Requirements:

- Never store plaintext passwords or reversible password encryption.
- Pick one normalization policy and enforce it at creation/update.
- Do not require customer accounts for public menu browsing; staff identity is separate from public QR access tokens.
- Avoid collecting customer PII unless a verified business requirement requires it.

### 2.4 `roles`, `permissions`, `role_permissions`, `restaurant_memberships`

Use a permission-based authorization model, not frontend-only role checks.

- `permissions`: global, code-managed catalog such as `orders.read`, `orders.create`, `orders.confirm_qr`, `orders.cancel`, `kitchen.update`, `bills.issue`, `payments.record_cash`, `payments.refund`, `menu.manage`, `inventory.manage`, `reports.read`, `staff.manage`, `settings.manage`, and `audit.read`.
- `roles`: `id`, `restaurant_id`, `name`, `is_system_template`, timestamps. Unique constraint on `(restaurant_id, normalized_name)`. Provision standard role templates for owner, manager, waiter, kitchen, and cashier; each restaurant's assignments remain explicit.
- `role_permissions`: `(restaurant_id, role_id, permission_key)` with a foreign key to role and valid permission. Avoid role/permission rows from another tenant.
- `restaurant_memberships`: `id`, `restaurant_id`, `user_id`, `role_id`, `status` (`INVITED`, `ACTIVE`, `SUSPENDED`, `REVOKED`), `joined_at`, `invited_by_membership_id`, `created_at`, `updated_at`. Unique active membership policy for `(restaurant_id, user_id)`; enforce via constraint or transaction.

Each protected request must resolve an active membership and permission for the requested tenant. User-supplied `restaurant_id` must never grant access by itself. When a user belongs to multiple restaurants later, the active restaurant context must be revalidated on every request.

### 2.5 `refresh_sessions` (or `refresh_tokens`)

For rotating refresh-token authentication, store only a hash of the opaque refresh token, plus `id`, `user_id`, `token_family_id`, `expires_at`, `revoked_at`, `replaced_by_session_id`, `created_at`, `last_used_at`, and coarse device metadata. Detect reuse of a revoked token and revoke its family according to the security design. Never log raw tokens.

## 3. Tables, QR credentials, and dining sessions

### 3.1 `restaurant_tables`

Fields: `id`, `restaurant_id`, `table_code`/`table_number`, `display_name`, `seating_capacity` (optional), `status` (`ACTIVE`, `OUT_OF_SERVICE`, `ARCHIVED`), `sort_order`, timestamps.

Constraint: unique `(restaurant_id, table_code)`. A table is not itself a dining session. Do not use a table's simple `occupied` boolean as the only representation of an open order/session.

### 3.2 `table_qr_codes`

Fields: `id`, `restaurant_id`, `table_id`, `token_hash`, `status` (`ACTIVE`, `REVOKED`), `created_at`, `created_by_membership_id`, `revoked_at`, `last_rotated_at`.

Rules:

- Generate a cryptographically random, high-entropy token; store only a one-way hash in the database. The raw token exists only for generation/display of the QR URL.
- Use unique `token_hash`; never use sequential IDs as QR credentials.
- QR tokens may identify a table and published menu, but must not authorize access to a table's full history, bill, customer personal data, or staff actions.
- Provide revocation/rotation if a QR code is compromised. Rate-limit public resolve/order endpoints.
- Because physical QR codes can be copied, require staff confirmation and limit customer access to minimal data.

### 3.3 `dining_sessions`

One visit/occupancy period at one table. Candidate fields:

- `id`, `restaurant_id`, `table_id`
- `session_number` (optional, human-readable per restaurant/business day)
- `status`: `OPEN`, `CHECKOUT_PENDING`, `CLOSED`, `VOID`
- `opened_at`, `opened_by_membership_id`, `closed_at`, `closed_by_membership_id`
- `version` for optimistic concurrency; timestamps

Invariants:

- At most one active session per table. Enforce with a PostgreSQL partial unique index for status `OPEN`/`CHECKOUT_PENDING`, or an equivalent transactionally safe mechanism.
- A closed session cannot accept new items without a deliberate reopen/administrative workflow and audit record.
- When accepting a QR order, attach it to the active session or atomically create a new one if policy allows. Two concurrent acceptances must not create two active sessions.
- The business-day/session-number policy remains configurable and must be confirmed.

### 3.4 `service_calls`

Guest "Call waiter" requests from the QR website, and kitchen "food ready for pickup" signals from the kitchen screen. Candidate fields: `id`, `restaurant_id`, `kind` (`GUEST`, `KITCHEN`), `table_id`, `kitchen_ticket_id` (nullable, set for `KITCHEN` calls), `detail` (free-text snapshot of what the call is about, e.g. the pickup summary), `status` (`REQUESTED`, `ACKNOWLEDGED`), `created_by_membership_id` (nullable, kitchen actor for `KITCHEN` calls), `created_at`, `updated_at`, `acknowledged_at`, `acknowledged_by_membership_id` (nullable).

Invariants:

- Requests are scoped to the QR-owned table only; no customer identity is stored.
- While a `REQUESTED` call of the same `kind` is open (per table for `GUEST`, per ticket for `KITCHEN`), duplicates are collapsed (server-side dedupe returns the existing call). A partial unique index on active `REQUESTED` calls per table/kind is acceptable if dedupe is later moved into the DB layer.
- Acknowledgement is a staff action requiring `tables.manage` and an append-only audit entry; acknowledge is idempotent for already-`ACKNOWLEDGED` rows.
- `KITCHEN` calls are created by `kitchen.update` holders via the ticket call-waiter domain operation, which in one transaction forces the ticket's open items to `READY`, records audit and an outbox `service_call.requested` event.

## 4. Menu catalog

### 4.1 `menu_categories`

Fields: `id`, `restaurant_id`, `name`, `description`, `display_order`, `status` (`DRAFT`, `PUBLISHED`, `ARCHIVED`), `created_at`, `updated_at`.

Unique normalized name per restaurant may be appropriate if the restaurant does not need duplicate category labels. Do not require it without confirming localization/multiple-menu needs.

### 4.2 `menu_items`

Fields: `id`, `restaurant_id`, `category_id`, `sku` (optional), `name`, `description`, `image_object_key` (optional), `current_price_minor`, `currency_code`, `status` (`DRAFT`, `PUBLISHED`, `UNAVAILABLE`, `ARCHIVED`), `is_vegetarian`/dietary tags only if validated, `display_order`, `ingredients_text` (display-only, max 500 chars), timestamps.

`ingredients_text` is a guest-facing free-text display of ingredients/allergens (including an explicit "Contains:" line when known). It is presentation text, not structured allergen data; do not derive machine-readable allergens or inventory consumption from it.

Rules:

- `current_price_minor >= 0`; validate currency matches the restaurant's configured currency.
- Public customers see only published, currently orderable items.
- Backend rechecks availability and current allowed price when accepting/submitting according to the price-lock policy. Historical order lines must retain snapshots even if the menu item is renamed, repriced, or archived.
- Changing `category_id` must not invalidate historical order lines. Use nullable historical references or `ON DELETE RESTRICT`/archive strategy rather than cascading deletion.

### 4.3 `menu_option_groups` and `menu_options`

Use these only for real menu customization requirements, such as size or add-ons.

- `menu_option_groups`: `id`, `restaurant_id`, `name`, `selection_min`, `selection_max`, `required`, display order, status.
- `menu_options`: `id`, `restaurant_id`, `group_id`, `name`, `price_delta_minor`, `status`, display order.
- A join table links option groups to applicable menu items if groups are reusable.
- Validate selection counts and option/menu-item tenant ownership on the server. Snapshot selected labels and price deltas into each order item; do not recalculate old orders from current option prices.

### 4.4 Menu images

Store images in object storage and keep only a controlled object key/metadata in the database. Validate content type, actual file signature, size, and image decoding; scan uploads as appropriate. Never trust a file extension alone or accept arbitrary object paths from a client.

## 5. Orders and kitchen workflow

### 5.1 `orders`

Fields:

| Column | Purpose |
|---|---|
| `id` UUID PK | Stable order identifier |
| `restaurant_id` | Tenant scope |
| `table_id` | Required table association |
| `dining_session_id` | Nullable while a QR request is awaiting staff acceptance; assigned on acceptance |
| `source` | `WAITER` or `CUSTOMER_QR` for the initial dine-in scope |
| `status` | `PENDING_CONFIRMATION`, `ACCEPTED`, `REJECTED`, `CANCELLED`, `COMPLETED` |
| `created_by_membership_id` | Null for anonymous customer requests; otherwise staff actor |
| `idempotency_key` | Required for retry-safe submissions; scoped and unique |
| `customer_status_token_hash` | Hash of a high-entropy read-only token for status lookup; never an authorization grant for orders/bills |
| `customer_note` | Optional, length-limited, sanitized display text |
| `submitted_at`, `accepted_at`, `rejected_at`, `cancelled_at`, `completed_at` | Lifecycle timestamps |
| `decision_by_membership_id` | Staff actor for accept/reject/cancel action as applicable |
| `rejection_reason_code`, `rejection_note` | Structured reason and optional sanitized note |
| `version`, `created_at`, `updated_at` | Concurrency/history metadata |

Indexes/constraints: `(restaurant_id, status, submitted_at)`, `(restaurant_id, table_id, created_at)`, unique `(restaurant_id, idempotency_key)` for submission keys (or an equivalent idempotency ledger with defined scope), and tenant-consistent FKs.

Order invariants:

- Customer QR orders start at `PENDING_CONFIRMATION`; they cannot create a kitchen ticket before authorized staff acceptance.
- Waiter-created orders may be created/accepted as part of an authorized “send to kitchen” operation, but this action must be explicit and audited.
- Acceptance, session attachment/creation, kitchen-ticket creation, and outbox/audit writes happen atomically.
- Rejection or cancellation records actor, time, and reason where practical. Never erase the original submitted order.
- Use optimistic locking or row locks to prevent a concurrent accept/reject/cancel race.
- `customer_status_token_hash` grants read-only access to that order's limited status only. Do not return the full bill, other orders at the table, staff identities, or internal notes through the public endpoint.

### 5.2 `order_items`

Fields: `id`, `restaurant_id`, `order_id`, `menu_item_id` nullable for historical retention, `item_name_snapshot`, `item_sku_snapshot` optional, `quantity` (positive integer for food portions unless a validated requirement needs fractional quantity), `unit_price_minor`, `discount_minor`, `tax_minor`, `line_total_minor`, `currency_code`, `tax_snapshot` JSONB, `special_instructions`, `created_at`, `updated_at`.

Constraints: quantity > 0; amount fields nonnegative where policy requires; all amounts/currency derive from server-calculated values; tenant-consistent FK to order/menu item; line-total formula checked in application/domain tests and, where practical, DB check constraints.

Selected options should be stored in `order_item_options` with stable identifiers where available and snapshot columns (`option_name_snapshot`, `price_delta_minor`, quantity/count). Do not rely on current menu option rows for historical prices.

Amendment policy: after acceptance, changes that affect kitchen production or totals must become explicit additions, cancellations, or amendment/audit events. Do not overwrite accepted item snapshots without history. The exact workflow for replacing an item or changing quantity must be confirmed before implementation.

### 5.3 `kitchen_tickets` and `kitchen_ticket_items`

Initial scope may use one ticket per accepted order, while the schema can permit multiple tickets later if there is a real need for kitchen stations.

`kitchen_tickets` fields: `id`, `restaurant_id`, `order_id`, `ticket_number`, `status` (`NEW`, `IN_PROGRESS`, `READY`, `CANCELLED`), `created_at`, `started_at`, `ready_at`, `cancelled_at`, `last_updated_by_membership_id`, timestamps. Add a unique/idempotent rule to avoid two active tickets for the same order under the pilot policy.

`kitchen_ticket_items` fields: `id`, `restaurant_id`, `ticket_id`, `order_item_id`, `status` (`NEW`, `PREPARING`, `READY`, `SERVED`, `CANCELLED`), `quantity_snapshot`, `instructions_snapshot`, `started_at`, `ready_at`, `served_at`, `cancelled_at`, `updated_by_membership_id`, timestamps.

Rules:

- An active ticket references an accepted order only.
- Kitchen users can update only permitted preparation states; they cannot change prices or mark payments paid.
- Aggregate ticket status must be updated in the same transaction as item state or calculated consistently from item states.
- A cancelled item already in preparation requires an explicit policy and may need manager acknowledgement; do not silently remove it from the screen or financial history.
- Real-time events are notifications. Clients refetch current ticket state after reconnecting.

## 6. Bills and payments

### 6.1 `bills`

Proposed pilot policy: one bill per dining session initially, with split-bill allocation deferred unless validated. Fields:

- `id`, `restaurant_id`, `dining_session_id` (unique for one-bill-per-session policy)
- `status`: `OPEN`, `ISSUED`, `PARTIALLY_PAID`, `PAID`, `VOID`
- `currency_code`, `subtotal_minor`, `discount_minor`, `tax_minor`, `service_charge_minor`, `total_minor`, `paid_minor`, `balance_due_minor`
- `issued_at`, `paid_at`, `voided_at`, `voided_by_membership_id`, `void_reason`
- `version`, timestamps

Totals are server-generated from bill line snapshots and approved adjustments. Do not accept client-supplied totals as authoritative. The policy for tips/service charges/tax must be confirmed and configured.

For concurrent edits and payment safety:

- Issuing a bill freezes its current version for payment initiation.
- If an accepted order or authorized amendment changes the amount, explicitly invalidate/reissue the bill under an audited operation; do not silently mutate a bill while an online payment is processing.
- If a payment attempt is pending or provider outcome is unknown, reconcile it before creating a conflicting new charge or materially changing the bill.
- Closed/paid bills cannot be casually reopened. Use a permissioned correction/refund workflow.

### 6.2 `bill_items`

Fields: `id`, `restaurant_id`, `bill_id`, `order_item_id` (unique under a policy that bills each accepted item once), `description_snapshot`, `quantity`, `unit_price_minor`, `discount_minor`, `tax_minor`, `line_total_minor`, `tax_snapshot`, `created_at`.

Do not cascade-delete bill items when a menu item or order changes. Adjustments should be separate auditable lines/events rather than hidden edits to a settled bill. Define whether cancelled/unserved items are charged according to business and local law before launch.

### 6.3 `payments`

Each attempt or tender is a separate row. Fields:

- `id`, `restaurant_id`, `bill_id`, `method` (`CASH`, `ONLINE_PROVIDER`, and only other validated methods)
- `status`: `INITIATED`, `PENDING`, `SUCCEEDED`, `FAILED`, `CANCELLED`
- `amount_minor`, `currency_code`, `provider` nullable for cash, `provider_payment_id` nullable, `idempotency_key`, `initiated_by_membership_id` nullable for customer-initiated online checkout
- `created_at`, `updated_at`, `succeeded_at`, `failure_code`, sanitized `provider_metadata`

Constraints and invariants:

- Unique `(restaurant_id, idempotency_key)` for client/server retry keys under a defined endpoint scope.
- Unique `(provider, provider_payment_id)` when provider IDs exist.
- A provider payment is never successful solely because the browser returned to a success URL.
- Verify signed webhooks and/or perform authenticated provider status lookups; validate provider, amount, currency, bill/reference, and expected state before settling.
- Use a database transaction for state change, bill paid/balance recomputation, audit, and outbox event.
- An amount must not exceed the remaining balance unless an explicit overpayment/refund policy exists. Concurrency must not allow two simultaneous tenders to over-settle the same bill.
- Cash tender is marked successful only after the authorized cashier records the actual received amount.
- Never store PAN/card verification codes or other sensitive card data. Use a compliant payment provider's hosted checkout/tokenization path.

### 6.4 `payment_webhook_events`

Fields: `id`, `provider`, `provider_event_id`, `received_at`, `signature_verified`, `processing_status`, `processed_at`, `payload_hash`, sanitized metadata/error code.

Unique `(provider, provider_event_id)`. A repeated webhook must be safe to receive many times. Reject invalid signatures; do not trust an event ID without verifying authenticity. Avoid storing unrestricted raw payloads where they may contain personal/payment information.

### 6.5 `refunds`

Fields: `id`, `restaurant_id`, `payment_id`, `amount_minor`, `currency_code`, `status` (`REQUESTED`, `PENDING`, `SUCCEEDED`, `FAILED`, `CANCELLED`), `reason_code`, `reason_note`, `requested_by_membership_id`, `approved_by_membership_id`, `provider_refund_id`, timestamps.

Refunds must be permissioned, idempotent, auditable, and bounded by refundable settled amount. A refund is not complete merely because a request was sent to a gateway.

### 6.6 Payment and refund state derivation

Do not store one ambiguous `order.payment_status` as the source of truth. Derive the bill settlement status from successful tenders applied to the issued bill and its balance, with a materialized bill balance updated in the same transaction and periodically reconciled. Track refunds as separate records linked to the original successful payment; a refund must not silently make the original bill “unpaid” or reopen it. If a refund requires a financial correction/credit note under the restaurant’s policy or local law, model that as a separate, auditable adjustment document/workflow. Expose separate, clear values to clients for bill settlement and refund state (for example: bill paid; refund pending).

## 7. Inventory and purchasing (phase-gated)

### 7.1 `ingredients`

Fields: `id`, `restaurant_id`, `name`, `sku` optional, `base_unit_code` (`g`, `ml`, `each`, etc. based on approved unit catalog), `reorder_level_base_qty`, `is_active`, timestamps.

Use one canonical base unit per ingredient. Conversions from purchasing units must be explicit (e.g. case to each, kilogram to gram), validated, and tested. Avoid mixing “kg” and “g” in balance calculations without normalization.

### 7.2 `recipes` / `recipe_ingredients`

`recipes`: `id`, `restaurant_id`, `menu_item_id`, `version`, `yield_quantity`, `status`, `effective_from`, timestamps.  
`recipe_ingredients`: `id`, `restaurant_id`, `recipe_id`, `ingredient_id`, `quantity_in_base_units`, `waste_factor` if required, timestamps.

Recipe versions must preserve how consumption was calculated for historical sales. Do not retroactively recalculate past consumption using a newly edited recipe unless the report explicitly presents a restated estimate.

### 7.3 `stock_movements`

Append-only inventory ledger: `id`, `restaurant_id`, `ingredient_id`, `movement_type` (`PURCHASE_RECEIPT`, `SALE_CONSUMPTION`, `WASTE`, `ADJUSTMENT_IN`, `ADJUSTMENT_OUT`, `RETURN`, `REVERSAL`), `quantity_delta_base_units` signed `NUMERIC`, `unit_cost_minor` optional, `currency_code` optional, `reference_type`, `reference_id`, `reason_code`, `actor_membership_id`, `occurred_at`, `created_at`, metadata. Corrections should create reversing/correcting movements, not edit the original ledger row.

`ingredient_stock_balances` may be maintained as a performance cache, but it must be updated transactionally with the movement ledger and rebuildable from it. Document the reconciliation job.

### 7.4 Suppliers and purchasing

Candidate tables: `suppliers`, `purchase_orders`, `purchase_order_items`, and `goods_receipts`. Keep ordering and stock receipt separate: creating a purchase order should not increase available stock; receiving goods should create stock movements. Track ordered, received, cancelled, and outstanding quantities with a defined policy.

### 7.5 Inventory timing

Inventory is a confirmed product area but exact launch scope is not settled. Build/validate the order-billing-kitchen path first. Do not claim real-time ingredient stock accuracy until recipe consumption, wastage, purchase receiving, stock counts, cancellations, and reversals are implemented and reconciled.

## 8. Audit and asynchronous work

### 8.1 `audit_events`

Append-only fields: `id`, `restaurant_id`, `actor_user_id` nullable, `actor_membership_id` nullable, `action`, `entity_type`, `entity_id`, `occurred_at`, `request_id`, `ip_address`/coarse metadata where legally appropriate, `user_agent` bounded, `before_snapshot` and `after_snapshot` with sensitive fields redacted.

Audit sensitive actions including QR accept/reject, order amendments, cancellations, price changes, discounts, bill issue/void, cashier payments, refunds, role/permission changes, menu availability changes, and stock adjustments. Protect audit read/export access. Never put credentials, access tokens, raw payment secrets, or unnecessary PII in snapshots.

### 8.2 `outbox_events`

Fields: `id`, `restaurant_id`, `event_type`, `aggregate_type`, `aggregate_id`, `payload` (versioned and minimized), `occurred_at`, `available_at`, `processed_at`, `attempt_count`, `last_error_code`.

Insert an outbox event in the same transaction as the underlying business state where reliable notification/background work is required. Consumers must be idempotent; delivery is at-least-once, not exactly-once. Avoid publishing secrets or large records in event payloads.

## 9. Tenant-safe relationship design

For tenant-owned relationships, use composite uniqueness such as `UNIQUE (restaurant_id, id)` where needed and composite foreign keys `(restaurant_id, parent_id)` to the parent's `(restaurant_id, id)`. This helps prevent a row in Restaurant A from referencing a parent in Restaurant B even if application validation fails.

Examples:

- An order's table and dining session must belong to its `restaurant_id`.
- An order item must reference an order in the same tenant and a menu item in the same tenant.
- A bill must reference a dining session in the same tenant.
- A payment must reference a bill in the same tenant.
- A kitchen ticket item must reference a ticket and order item in the same tenant.
- A membership role must belong to the same restaurant as the membership.

`ON DELETE CASCADE` is appropriate only for disposable dependent data with no historical or financial value. Use restrictive FKs or soft archive for historical entities.

## 10. Index baseline

Add indexes based on query plans and actual traffic. Expected initial indexes include:

- Tenant plus status/time: orders `(restaurant_id, status, submitted_at DESC)`, kitchen tickets `(restaurant_id, status, created_at)`, bills `(restaurant_id, status, created_at)`, payments `(restaurant_id, status, created_at)`.
- Table/session lookup: dining sessions `(restaurant_id, table_id, status)` plus the partial unique active-session index.
- Tenant and business identifiers: tables `(restaurant_id, table_code)`, categories/items `(restaurant_id, status, display_order)`, memberships `(restaurant_id, user_id, status)`.
- Foreign keys used for parent lookups and joins, including `order_items.order_id`, `bill_items.bill_id`, `payments.bill_id`, `stock_movements.ingredient_id`.
- Unique idempotency and provider references.
- Time indexes for audit/reporting scoped by tenant.

Do not add a large number of speculative indexes. Each index adds write cost and storage; verify representative query plans with `EXPLAIN (ANALYZE, BUFFERS)` in a safe test/staging dataset.

## 11. Required database-level invariants and tests

Before production, add migrations and tests proving:

1. An active table cannot have two active dining sessions.
2. A QR order cannot create an active kitchen ticket before staff acceptance.
3. Concurrent accepts cannot create duplicate tickets or duplicate sessions.
4. Duplicate submission idempotency keys do not create duplicate orders.
5. Provider transaction and webhook identifiers are unique and replay-safe.
6. Two simultaneous payments cannot over-settle a bill.
7. Money totals use one defined rounding policy and match line snapshots.
8. No cross-tenant foreign-key relationship can be written.
9. Historical order/bill snapshots remain available when catalog items change or are archived.
10. Stock balance can be rebuilt from the stock movement ledger.
11. Audit and ledger rows cannot be silently deleted/updated by ordinary application roles.
12. Every migration can be applied to an empty database and upgraded from the previous supported release.
